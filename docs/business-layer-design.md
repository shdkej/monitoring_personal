# Monitoring Metrics Catalog — 4 Layers × 8

## 목적과 측정 원칙

Grafana에서 비즈니스·고객·제품·시스템의 상태를 앱별로 살핀다. 각 레이어는 대표 지표 8개로 고정하되, 실제 원천이 연결되지 않은 값은 0으로 꾸미지 않고 `N/A`로 표시한다. 현재 저장소에 쿼리가 있다는 사실과 데이터가 실제로 유입된다는 사실은 구분한다.

- **GA4**: Space의 GA4 속성별 신규 사용자·세션. 4개 속성의 채널별 최근 7일 집계와 blog·afzma의 일간 직접 조회
- **PostHog**: 공유 프로젝트의 앱별 사용·재방문·품질. 판정 시도→저장 퍼널은 프로젝트 단위
- **CloudWatch / Prometheus**: 노드 계측은 연결됨. YACE exporter는 scrape되나 Lambda 유효 샘플·DynamoDB throttling·RUM 데이터는 확인되지 않음
- **이메일/CS**: 지정된 지원 수신함에서 최근 7일의 앱 태그 문의 대화를 집계한다. 메일 원문·개인정보는 모니터링에 저장하지 않는다.

## 레이어별 지표

상태: **연결됨**은 현재 원천 쿼리가 있음, **조건부**는 계측·정의·실데이터 확인이 더 필요함, **입력 필요**는 현재 쓸 수 있는 원천이 없음.

### 1. 비즈니스 — 앱별 사업 성과

| # | 지표 | 산출 기준 | 현재 상태 / 필요한 입력 |
|---|---|---|---|
| 1 | 북극성 지표 | 고객이 핵심 가치를 얻은 빈도 또는 규모 | 입력 필요: 앱별 핵심 가치·이벤트 정의 |
| 2 | 순매출 | 환불·할인 제외 매출 | 입력 필요: 결제/회계 원천과 통화·기간 |
| 3 | 매출 성장률 | 기간별 순매출 증감률 | 입력 필요: 같은 매출 원천의 기간 데이터 |
| 4 | 유료 고객 수 | 기간 내 결제 완료한 고유 고객 | 입력 필요: 결제 성공 이벤트/API |
| 5 | 유료 전환율 | 유료 고객 ÷ 적격 사용자 | 입력 필요: 분모·결제완료 정의 |
| 6 | 고객당 매출(ARPPU) | 순매출 ÷ 유료 고객 수 | 입력 필요: 매출과 유료 고객 데이터 |
| 7 | 환불률 | 환불액 또는 환불 건수 ÷ 결제액/건수 | 입력 필요: 결제·환불 원천 |
| 8 | 고객 획득 비용(CAC) | 캠페인 비용 ÷ 신규 유료 고객 | 입력 필요: 광고비와 채널별 유료 전환 연결 |

구독형 앱은 매출 성장률의 보조 지표로 MRR/구독 유지율을 추가할 수 있다. 모델을 확인하기 전에는 모든 앱에 MRR을 강제하지 않는다.

### 2. 고객·마케팅 — 획득부터 재방문까지

| # | 지표 | 산출 기준 | 현재 상태 / 필요한 입력 |
|---|---|---|---|
| 1 | 신규 사용자 | 앱별 GA4 신규 사용자 | Space GA4 피드 4개 속성의 지난 7일 값 |
| 2 | 유입 채널별 세션 | 앱·유입 채널별 세션 | 4개 속성의 지난 7일 전체·채널별 세션과 blog·afzma의 일간 채널 상세. 범례에 기간과 채널 표시 |
| 3 | 이탈 사용자 수 | 앞 7일간 페이지를 보고 최근 7일에는 방문하지 않은 사용자 | 앱별 PostHog 코호트 |
| 4 | 7일 재방문율 | 두 7일 구간에 모두 방문한 사용자 ÷ 앞 7일 방문자 | 앱별 PostHog 코호트. 분모가 없으면 N/A |
| 5 | 핵심 퍼널 이탈률 | 퍼널 시작자 중 완료 이벤트 미발생 비율 | 공유 프로젝트의 판정 시도·저장 이벤트. 시작자가 없으면 N/A |
| 6 | 첫 방문 핵심 작업 완료율 | 최근 7일 첫 방문 중 첫 세션에서 핵심 행동을 완료한 비율 | policycock 사례 열람, Virtue 덕행 저장. 분모가 없으면 N/A |
| 7 | 공유 링크 신규 방문자 수 | 공유 링크로 처음 관측된 동의 브라우저 수 | policycock·Virtue. 브라우저 데이터 삭제 또는 분석 동의 철회 후에는 이전 방문을 연결할 수 없음 |
| 8 | 고객 문의 수 | 최근 7일 제목 맨 앞에 지원 앱 태그가 붙은 수신 대화 수 | Grafana 등록 앱 전체에서 같은 대화는 앱별 한 번 집계 |

### 3. 제품 — 사용자가 겪는 품질

| # | 지표 | 산출 기준 | 현재 상태 / 필요한 입력 |
|---|---|---|---|
| 1 | 화면 전환 지연 p95 | CloudWatch RUM 탐색 시간 p95 | 입력 필요: Prometheus에 RUM 시계열이 아직 없음 |
| 2 | 세션당 참여시간 | GA4 속성별 지난 7일 총 참여시간 ÷ 총 세션 수 (초) | GA4 홈에서 일 단위로 갱신. 세션이 없는 속성은 N/A |
| 3 | 프론트엔드 예외 | PostHog `$exception` 건수 | 연결됨. PostHog 앱별 최근 7일 예외 건수 |
| 4 | Core Web Vitals | LCP·INP의 지정 백분위 | 부분 연결. 앱별 PostHog 실측 LCP·INP의 최근 30일 p75. 표본이 없으면 N/A |
| 5 | 로그인 성공률 | 성공 로그인 ÷ 로그인 시도 | 입력 필요: 로그인 시도·성공 이벤트 |
| 6 | 결제 성공률 | 성공 결제 ÷ 결제 시도 | 입력 필요: 결제 시도·성공·실패 이벤트 |
| 7 | 제품 세션 수 | 앱 내 고유 세션 수 | 연결됨. PostHog 앱별 UTC 기준 최근 완료 7일의 고유 세션 ID 수 |
| 8 | 핵심 작업 완료 건수 | UTC 최근 완료 7일의 앱별 핵심 행동 이벤트 건수 | policycock 사례 열람, miniapp-image-tools 이미지 변환 완료, Virtue 덕행 저장. 합성 이벤트 제외 |

CloudWatch RUM의 페이지 탐색 지연은 API 응답시간과 같지 않다. 서버/API p95·p99가 필요하면 앱별 서버 계측이나 CloudWatch 서비스 지표를 별도 연결한다. FID는 현재 Core Web Vitals의 상호작용 반응성 지표가 아니므로 새 대시보드에는 INP를 사용한다.

## 앱·데이터 원천 현황

- 2026-11-26 원천 대조에서 GA4 계정 3개와 속성 4개(blog, afzma, policycock, purple-place-bb6ce)를 확인했다. Grafana의 GA4 직접 연결 권한은 blog·afzma에 있으며, 네 속성의 공통 지표는 Space의 일간 집계 피드에서 읽는다.
- PostHog 접근 가능 프로젝트는 424014 한 개이다. 등록 범위는 policycock, miniapp-image-tools, Infinity, shdkej.com, Virtue와 앱 미지정이다. 최근 90일의 명시적 앱 ID는 policycock·miniapp-image-tools였다. 2026-11-26 전환 이후 `service="virtue"`도 Virtue 앱만 집계한다. 과거 시계열에는 공유 프로젝트 전체 값이 남아 있다. 앱별 패널은 `scope`를 사용한다.
- YACE exporter와 ServiceMonitor scrape target은 정상(up)이다. YACE `/metrics`에는 Lambda invocation/error 및 DynamoDB capacity metric names가 있지만, 확인 시 Lambda samples는 NaN, DynamoDB consumed capacity는 0, throttling series는 없었다. CloudWatch RUM 로그에는 `No metrics data found`가 반복되고 RUM Prometheus series도 없다. 값이 0인지 데이터/리소스 범위가 잘못됐는지 임의 추정하지 않는다.
- 노드 CPU·메모리·디스크·네트워크·헬스 시계열은 Prometheus에 있다. HPA와 black-box latency probe 시계열은 없다.
- SAM-PC의 읽기 전용 Gmail 조회는 제목 맨 앞의 [등록된 앱 이름]을 분류한다. [모두의정책]은 policycock의 별칭이다. [AI 브리핑]과 일반 메일은 집계에서 제외한다.
- 매출·결제·광고비 원천은 저장소와 배포 설정에서 확인되지 않았다. 관련 Grafana 패널은 계획된 `business_*` placeholder query로 N/A 상태이며 실제 exporter 지표가 아니다. 값이나 North Star를 추정하지 않는다.
- 고객 8번 패널은 customer_support_threads의 앱별 최근 7일 문의 수를 표시한다. 클러스터 exporter의 gog 수집 주기는 한 시간이며 관측값의 유효 기간은 3시간이다.

## 메트릭 구현 계약

- 앱별·기간별로 분리하고 집계 기간과 분모를 패널 설명에 표시한다.
- `0`은 실제로 관측한 0건, `N/A`는 미연결·미정의·분모 없음으로 구분한다.
- SLO/목표치를 합의하지 않은 지표에는 임의의 초록·노랑·빨강 기준을 적용하지 않는다. 현재 stat 카드는 중립 회색이며 `N/A`도 회색으로 표시한다.
- 새 지표를 추가할 때 exporter/Prometheus 쿼리와 Grafana 패널, 이 카탈로그의 상태를 같은 변경에서 갱신한다.
- PostHog exporter는 원천 쿼리만 맡고 추정식으로 수익·고객·지원 문의를 만들어 내지 않는다.
